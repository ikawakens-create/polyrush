# ADR-0008: 解数検証付きパズル生成層 (VerifiedPuzzleGenerator) の導入

## Status

Accepted (2026-05-27)

## Context

### 解決したい問題

仕様書 § 4.3.3 は「生成したパズルの解の数を数え、4 通り以上なら簡単すぎる
ため再生成する」と定めている。しかし現状の `PuzzleGenerator.construct()`
（Task 3 / PR #18）はこの検証を行っていない。

Task 4（PR #20）の解数分布調査で、easy 難易度・seed=2 のパズルが解 4 通り
であることが判明済みであり、仕様未達の実例が既に存在する。

### 現状の部品

Phase 1 で以下が develop にマージ済み（いずれも CLAUDE.md により変更禁止）：

- `PuzzleGenerator.construct({difficulty, seed, ...})`
  パズルを 1 個生成する。品質の良し悪しは判定しない。
  失敗時は `GenerationFailedException` を throw する。
- `PuzzleSolver.countSolutions({frame, shapes, limit})`
  枠への敷き詰め解数を limit で頭打ちして数える。判定は行わない。

Task 4 のレビュー結論として「採用・再生成の判断はソルバに持たせず、
呼び出し側に置く」ことが合意されている。本 ADR はその「呼び出し側」を
正式な層として設計するものである。

### 制約

- `puzzle_generator.dart` / `solver.dart` / `difficulty.dart` は変更禁止
  （CLAUDE.md「既存ファイル変更ポリシー」）。
- 座標系は (y, x) = (row, col)（ADR-0006）。
- ドメイン層のエラー伝達は `Result<T, E>` 型を用いる方針（仕様書 § 14.2、
  ADR-0005）。ただし `Result` 型は Phase 1 時点で domain 層に実装例がなく、
  本タスクが初の適用例となる。

### 既知の仕様の不整合（本タスクの対象外・申し送り）

仕様書 § 4.3.4 はシードを文字列（`uuid().substring(0,8)`）として記述するが、
実装の `construct()` は `int seed` を受け取る。この不整合の解消は将来の
オンライン対戦フェーズ（ステージ2）の課題であり、本 ADR では扱わない。

## Decision

解数検証を行う新しい層 `VerifiedPuzzleGenerator` を新規ファイルとして
追加する。以下、8 つの設計判断を確定する。

### 判断 1: 新規層として実装し、既存ファイルを変更しない

`construct()` を改造するのではなく、新ファイル
`lib/domain/puzzle/verified_puzzle_generator.dart` を追加する。

新層は既存の公開 API（`construct()` と `countSolutions()`）を
「呼ぶだけ」で成立し、変更禁止ファイルには一切手を加えない。
これにより CLAUDE.md / ADR-0007 のガードレールと衝突しない。
「生成（construct）」と「品質判定（verify）」という別の関心事を
別の部品に分離する設計でもある。

### 判断 2: 再生成は決定論的サブシードで行う

検証で却下したパズルを再生成する際、同じ seed で `construct()` を
呼び直すと同じパズルが返り無限ループとなる。これを避けるため、
元 seed と試行回数から 決定論的に サブシードを派生させる。

- 派生は自前の整数四則演算のみで行う（`hashCode` / `Object.hash` は
  実行間の一貫性が保証されないため使用禁止）。
- 同じ元 seed からは、どの端末・何回起動しても同じサブシード列が
  得られること。

補足: 決定論性が実際に必要となるのはオンライン対戦（ステージ2）で
あり、ソロ版（ステージ1）の範囲では必須ではない。本判断は将来の
ための前倒し実装と位置づける。Dart の int はプラットフォーム差が
あり（ネイティブ 64bit / Web は 53bit 超で精度低下）、サブシード
関数はオーバーフローしない範囲（32bit マスク等）で実装する。
オンライン対戦着手前に Web 環境での決定論性を再検証すること。

### 判断 3: 採用・却下の閾値

仕様書 § 4.3.3 に従う。

- 解 1〜3 通り: 採用
- 解 4 通り以上: 却下し再生成
- 解 0 通り: 異常（判断 4 参照）

`countSolutions` の `limit` 引数に 4 を渡すことで、解が 4 つ
見つかった時点で探索が打ち切られる（仕様書通りの早期終了）。
閾値 4 は名前付き定数とし、将来の調整余地を残す。

### 判断 4: セル数合計を新層側で自己検査し、解 0 の二義性を排除する

`countSolutions` は「shapes のセル数合計 ≠ frame のマス数」のとき、
探索せず 0 を返す実装になっている。このため戻り値 0 には
「(a) 真に解が存在しない」「(b) 渡した shapes が誤りで門前払いされた」
の二義性がある。

逆算生成法では、生成器自身の配置が必ず 1 つの解となるため、
正しい入力に対して解 0 は理論上発生しない。したがって解 0 は
「簡単すぎるパズル」ではなく実装バグのサインである。

新層は `countSolutions` を呼ぶ前に、自ら frame のマス数と
ブロックのセル数合計の一致を `assert` で検査する。これにより
上記 (b) を新層の責務として早期に検出し、解 0 の意味を
(a) のみに一意化する。万一 (a) が発生した場合もバグとして
扱い、警告ログを残す。

### 判断 5: 検証リトライ上限は 8 回、超過時はフォールバック

`construct()` 内部の配置リトライ（最大 10 回）とは独立に、
検証リトライ上限を 8 回 とする。両者は階層が異なる別物である
（下表参照）。8 は名前付き定数 `maxVerificationRetries` とする。

| リトライ | 場所 | 数える対象 |
|---|---|---|
| 配置リトライ（既存・10回） | `puzzle_generator.dart` 内部 | 1 個のパズルを組む途中での詰まり直し |
| 検証リトライ（新規・8回） | `verified_puzzle_generator.dart` | 簡単すぎるパズルを丸ごと没にする回数 |

検証ループの終了条件は 2 通りある：

- 8 回の試行すべてで `construct()` が例外を投げた場合
  → パズルを 1 個も生成できていない。失敗として `Result` の
    `Err`（判断 8）を返す。
- 8 回試行しパズルは生成できたが、すべて解 4 通り以上だった場合
  → フォールバックとして「解の数が最も少なかったパズル」を返す。
    これは失敗ではなく品質がやや劣る成功であり、`Ok` を返す。
    ただし仕様書 § 4.3.3 を満たさないため警告ログを必須とし、
    戻り値の `isFallback` を true とする（判断 7）。

試行の途中で `construct()` が例外を投げた回は、リトライを 1 回
消費して次のサブシードへ進む（即時中断しない）。

### 判断 6: construct() は公開のまま残し、ゲーム本体は新層を経由する

`construct()` は検証ツール（`tool/puzzle_inspector.dart`）や
テストが生のパズルを得るために公開のまま残す。

ただしゲーム本体（Phase 2 以降の画面・ゲームロジック）は、
パズル取得に必ず `VerifiedPuzzleGenerator` を経由する規約とする。
`construct()` を直接呼ぶと未検証パズルを使えてしまう「うっかり穴」が
残るが、ツール用途のために公開を維持する判断を意識的に採用する。

### 判断 7: 戻り値は検証メタデータを含む VerifiedPuzzle 型とする

`GeneratedPuzzle` は変更禁止のため、新たに `VerifiedPuzzle` 型を
定義し、以下を保持する：

- `puzzle`: 採用された `GeneratedPuzzle`
- `solutionCount`: 検証で数えた解の数（1〜3、フォールバック時は 4 以上）
- `attemptsUsed`: 採用までに要した試行回数
- `isFallback`: フォールバックで返したか（判断 5）

`solutionCount` 等は仕様書 § 12.2 の分析イベント `puzzle_generated` や、
難易度チューニングのためのデータ収集に用いる。

### 判断 8: エラー伝達は Result 型、E は GenerationError enum

新層の公開メソッドは `Result<VerifiedPuzzle, GenerationError>` を返す。

- 仕様書 § 14.2 / ADR-0005 の方針に従う。`Result` 型は呼び出し側に
  エラー処理をコンパイラレベルで強制でき、例外の見落としを防ぐ。
- 新層は、例外を投げる `construct()` を内部で try-catch し、
  結果を `Result` に変換する「境界層」として機能する。
- `E` は `GenerationError` enum とする。当面の値は
  `allAttemptsFailed`（8 回すべて construct が失敗）の 1 種のみ。
  enum とすることで、呼び出し側の `switch` による網羅性チェックが効く。

呼び出し側（将来の Phase 2）は、`Result` の `Ok` / `Err` 両方を
必ず分岐処理すること。`Err` を握りつぶしてはならない。

## Consequences

### ポジティブ

- 仕様書 § 4.3.3 の品質保証が初めて実際に機能する。easy/seed=2 の
  既知問題が解消される。
- 変更禁止ファイルに一切触れないため、ADR-0007 が問題視した
  「確定資産の破壊」リスクがゼロ。
- `Result` 型の domain 層における初の実装例となり、後続タスクの
  手本となる。
- 検証メタデータ（`solutionCount` 等）が将来の難易度チューニングと
  分析イベントの基礎データになる。

### ネガティブ

- `Result` 型を domain 層で初めて使うため、新規セッションや
  レビュー担当が「なぜ既存 2 ファイルと作法が違うのか」と疑問を
  持つ可能性がある。
  → 対処: 新層の dartdoc に Result 採用理由（§ 14.2、例外の
    取りこぼし防止、construct の例外を変換する境界である旨）を明記し、
    本 ADR へのリンクを添える。
- 検証リトライ（8）と配置リトライ（10）の 2 つの上限が存在する。
  → 対処: 両者は階層の異なる別物。判断 5 の対比表を ADR に残し、
    コードでは `maxVerificationRetries` 等の説明的な定数名を用いる。
- フォールバック時に仕様書 § 4.3.3 を満たさないパズル（解 4 以上）が
  ユーザーに提示されうる。
  → 対処: 警告ログを必須とし、`isFallback` フラグで観測可能にする。
    没率が高い場合は生成器・難易度設定の見直しを井川へ報告する。

### 中立・申し送り

- 検証リトライ上限 8 の妥当性は、難易度ごとの「却下率」に依存する。
  Task 5 のテストで難易度別に多数シードを生成し却下率を実測すること。
  却下率が想定外に高い場合、8 という値ではなく生成器・難易度設定
  そのものの見直しが必要なサインであり、井川へ報告する。
- 仕様書 § 4.3.4（seed 文字列）と実装（seed int）の不整合は
  ステージ2 の課題として引き続き保留する。
