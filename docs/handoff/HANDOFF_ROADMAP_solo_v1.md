## 2. 今回 Fable が確定した設計方針

### 2-1. 反転操作を独立PRとしてスクランブルの前に入れる

理由（必読）: スクランブル（初期向きランダム化）は
PolyominoTransformer.allUniqueOrientations から初期向きを選ぶが、
これには反転した向きが含まれる。反転操作なしでスクランブルを先に入れると、
「回転だけでは絶対にはめられない向き」で配られたピースが詰みになる。
よって実装順は 反転 → スクランブル が必須。

反転の操作方法は「ダブルタップで反転」を Fable 推奨とする
（タップ=回転と競合せず、誤反転もダブルタップで復帰可能なため）。
最終決定は井川さんの実機確認後。ADR-0019 の追補として1段落追加する形で文書化
（新ADR不要）。

### 2-2. Phase 3 で生成方式を「枠ファースト」に転換する（ADR-0020 候補）

実物ウボンゴのカード分析から得た知見:
- 1つの枠を6通りの異なるピースセットで解けるようデザインされている
- 枠は外接矩形 4×4〜5×6、充填率 目測85〜95%、凹み1〜3箇所の「ずんぐり型」に統一
- 1タスクのピース数は3個（易）/4個（難）— 現行 easy=3 / normal=4 と一致

転換内容:
- 現行「ピース選択 → 積み上げで枠生成 → 検証」を
  「良い枠を先に生成 → その枠を敷き詰め可能なピースセットをソルバで列挙 → 採点して採用」に逆転
- 期待効果: 極端な枠形状と同一パズル問題の根本解決、1枠から複数セット取得によるバリエーション増、
  将来のタイムアタック/デイリーチャレンジ（全員同じ枠）の下地
- 衝突しない根拠: UI層は VerifiedPuzzle（完成品データ）しか見ておらず生成過程に非依存。
  ソルバ・puzzle_metrics・ピース定義・回転変換・単連結チェック・解数1〜3検証（ADR-0008/0010）は
  すべて流用。V3 は削除せず切替式で並存（B案方式）。
  ADR-0018 の非自明性フィルタは「生成後のふるい」から「枠生成時の条件」へ役割移行し、
  ADR-0020 内で意図の引き継ぎを明記する。
- 実装前に計測必須（測ってから組み込む原則）:
  ランダム枠に対し敷き詰め可能セットが何個・何msで見つかるかをCIテストで計測し、
  実用性を確認してから ADR-0020 を確定する。

### 2-3. Phase の順序原則

Phase 2 完了（スクランブルまで）→ Phase 3（枠改善）の順を厳守。
スクランブルが入って初めて難易度が本物になるため、その状態でないと
枠改善の効果を実機で正しく評価できない。
Phase 4（rush要素）は「パズル本体が気持ちいい」前提で乗せる演出のため最後。

### 2-4. ② forgiveness の方向確定（Fable, 2026-07-04）

方向は B（③スクランブルへ統合）で確定。当初案「easy の最小解数を上げる」は、
効果が間接的かつ現ソルバ（countSolutions のみ・変更禁止）では直接測れないため見送り。

forgiveness は「偶然一致の上限（K）」ではなく「下限（floor）」で設計する:
- easy: floor=1 / cap=1 → 崩せるピースのうち必ず 1 個を解の向きのまま配る
  （毎回ちょうど 1 個がそのまま置け、残り 2 個を回す体験を保証）。
- normal/hard: floor=0 / 従来の K 上限のみ。

easy のスクランブルは「解の向きからの回転のみ」で振る（反転向きは配らない）。
normal/hard は全ユニーク向き（反転込み）。よって easy はタップ回転だけで必ず解ける。
これが ②.5（反転UI）→ ③ の順序が必要な理由（反転の必要は normal/hard 側にある）。

実装は ③ に統合し、ADR-0019 の追補として floor/cap 方式と easy 回転限定を
③ 設計時に文書化する。②a（下表）はその前段の計測のみ。
